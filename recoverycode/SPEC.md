# Muun Recovery Code Specification

This document specifies the recovery code formats supported by libwallet's
`recoverycode` package. It is written so that a third-party wallet can
implement validation, typo location and key derivation without reading the Go
code. The test vectors in [`testdata/v3_vectors.json`](testdata/v3_vectors.json)
are normative. They are generated by an independent reference implementation,
[`testdata/gen_vectors.py`](testdata/gen_vectors.py).

## 1. Alphabets

| Name | Characters | Size |
|---|---|---|
| `Alphabet` | `ABCDEFHJKLMNPQRSTUVWXYZ2345789` | 30 |
| `AlphabetLegacy` | `ABCDEFHJKMNPQRSTUVWXYZ2345789` | 29 (no `L`) |

`idx(c)` is the 0-based position of `c` in `Alphabet`.

Codes are shown in **blocks of 4 symbols separated by `-`**. "Symbols" always
means the code with the dashes removed.

## 2. Versions

| Version | Prefix | Symbols | Blocks | Length with dashes | Checksum |
|---|---|---|---|---|---|
| 1 (legacy) | any, but never `L` | 32 from `AlphabetLegacy` | 8 | 39 | none |
| 2 | `LA` | `L` + `A` + 30 random | 8 | 39 | none |
| 3 | `LB` | `L` + `B` + 30 random + 4 checksum | 9 | 44 | block 9 |

The version of a code that starts with `L` is `idx(code[1]) + 2`. The highest
version this specification defines is **3**.

Example v3 code: `LBZC-MYTK-E9P3-7C7B-AHJN-KX79-22CY-WAY7-K7QZ`

## 3. The v3 checksum

Let `body` be symbols 0–31 (`L`, `B` and the 30 random symbols).

```
P  = 887
S1 = ( Σ_{i=0..31} (i+1)  · idx(body[i]) ) mod P
S2 = ( Σ_{i=0..31} (i+1)² · idx(body[i]) ) mod P

enc(v)  = Alphabet[v div 30] , Alphabet[v mod 30]
block 9 = enc(S1) , enc(S2)
```

To decode a pair of symbols `c0 c1`, compute `dec(c0 c1) = idx(c0)·30 + idx(c1)`.
A pair that decodes to a value `≥ 887` is invalid.

A v3 code is valid only if `dec(symbols[32:34]) = S1` and `dec(symbols[34:36]) = S2`.

**Properties.** P is prime, every weight is in 1–32 and every symbol difference is in 1–29, so all of them are nonzero mod P. Because the weights form a Vandermonde system, the code has minimum distance 3:
- every error in 1 or 2 symbols is detected, including any transposition
- a random string is accepted with probability ≈ 1/810,000
- every code with exactly one wrong symbol is at distance 1 from exactly one valid code (§6)

## 4. Validation (`Version` / `Validate`)

Validation is **strict**: the input must already be canonical (uppercase, dashes in place, no whitespace). Use `Normalize` (§5) on user input first.

The checks run in this order. The first failure determines the error kind.

1. If the code has at least 2 characters and starts with `L`:
   1. If `code[1]` is not in `Alphabet`, or `idx(code[1]) + 2 > 3` → **version** error.
   2. The expected length is 39 for v2 and 44 for v3. Any other length → **length** error.
   3. Every 5th character must be `-` and every other character must be in `Alphabet`; otherwise → **characters** error.
   4. For v3, if the checksum doesn't match (including a pair value `≥ 887`) → **checksum** error.
2. Otherwise (legacy):
   1. A length other than 39 → **length** error.
   2. Every 5th character must be `-` and every other character must be in `AlphabetLegacy`; otherwise → **characters** error.
   3. The code is version 1.

## 5. Normalization (`Normalize`)

`Normalize` turns user input into the canonical form that validation and key derivation expect:

1. Uppercase the input, then remove every `-` and every whitespace character.
2. Find the expected symbol count:
   - if the result starts with `L` and has at least 2 symbols, read the version from symbol 1: v2 needs 32 and v3 needs 36, and an unknown version is a **version** error
   - otherwise it is a legacy code, which needs 32
3. A different count → **length** error.
4. Insert a `-` after every 4 symbols.

`Normalize` does **not** check the alphabet or the checksum. Run validation on its output.

## 6. Typo location (`LocateTypo`)

For an input that is *not* a valid v3 code:

1. Uppercase the input, then remove every `-` and every whitespace character. It must have exactly 36 symbols; otherwise there is no result.
2. If more than one symbol is outside `Alphabet`, there is no result. If exactly one is, only that position is a candidate. Otherwise all 36 positions are candidates.
3. For every candidate position and every replacement symbol in `Alphabet`, build the code and keep it if it is a valid v3 code (§4).
4. If exactly one valid code was found, return its position (0-based symbol index, dashes excluded) and the canonical corrected code. Otherwise there is no result.

A valid input has no result.

Callers need not search exhaustively. The closed form below is an equivalent shortcut for body errors: compute the syndromes `d1 = S1 − dec(pair1)` and `d2 = S2 − dec(pair2)` (mod P). If both are nonzero, the typo is at 1-based position `w = d2·d1⁻¹`, and the correct symbol index is `idx(body[w−1]) − d1·w⁻¹` (mod P).

**A located typo is only a suggestion.** An input with 2 or more errors can be at distance 1 from a *different* valid code. Applying the suggestion silently would then derive the wrong key.

## 7. Key derivation

| Version | Private key (32 bytes, secp256k1 scalar) |
|---|---|
| 1 | `scrypt(password = code, salt = hex-decoded salt, N = 512, r = 8, p = 1, len = 32)` |
| 2, 3 | `HMAC-SHA256(key = "muun:rc", message = code)` |

`code` is the canonical string **including dashes**: 39 bytes for v1/v2 and 44 bytes for v3. The salt applies only to v1.

## 8. Error kinds

| Kind | Meaning |
|---|---|
| `length` | Wrong number of characters (or symbols, for `Normalize`) for the detected version |
| `characters` | A character outside the alphabet, or a misplaced dash |
| `version` | Unknown version character |
| `checksum` | v3 checksum mismatch. The code is well-formed but contains a typo |
