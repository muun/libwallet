**Deviations from the plan below**
- `LocateTypo` searches every single-symbol replacement (36 × 29 candidates) rather than using the closed-form syndrome. It's simpler, covers errors in the header and in block 9 the same way, and also handles one symbol outside the alphabet (such as `O`). The closed form is documented in the spec as an equivalent shortcut.
- `RecoveryCodeBlockCount` takes a code *prefix* (at least the first 2 symbols, any case or separators) instead of a single version char.
- `RecoveryCodeTypo` also carries the 0-based `Position`.
- `go.mod` was not bumped (open question 1). Fuzzing is done with a seeded random-input test instead of native fuzzing, so the code still builds with Go 1.14.
- **A bug fixed along the way:** `randChar` computed its rejection threshold as `-clen % clen`, which is always 0 for Go's signed ints. As a result the first 16 alphabet symbols were drawn with probability 9/256 instead of 8/256 (about 0.1 bits of entropy lost per code, v2 included). It now uses `256 % clen`.
- Tests measured that about 0.3% of random 2-symbol errors (55 of 20,000) get a (wrong) single-symbol suggestion. This is the expected rate for a distance-3 code, and it's why suggestions are hints only.

## 1. Background

### 1.1 How v2 works today

Source: `recoverycode/recoverycode.go` (exposed to gomobile through `recoverycode.go` in the root package).

| Property | v2 today |
|---|---|
| Layout | `L` + version char + 30 random chars = 32 chars, shown as 8 blocks of 4 with dashes (39 chars) |
| Example | `LA2Q-48Z3-25JR-S5JB-5SUS-HXHJ-RCMM-8YUA` |
| Alphabet | `ABCDEFHJKLMNPQRSTUVWXYZ2345789` (30 symbols, look-alike characters removed) |
| Version encoding | `Alphabet[version-2]`, so v2 = `A`. A v3 code starts with `LB`. |
| Entropy | 30 × log2(30) ≈ **147.2 bits** |
| Key derivation | `HMAC-SHA256(key="muun:rc", msg=<full dashed code string>)` → secp256k1 private key (the "challenge key") |
| Validation | `Version()` checks the length (hardcoded to 39), the dash positions, the alphabet and the version char. **It does not check integrity.** |

v1 (legacy) codes have no `L` prefix and use `AlphabetLegacy` (which has no `L`) plus a scrypt salt. They don't affect this plan beyond staying supported.

### 1.2 The problem

Any 39-character string with the right alphabet and dash positions passes `ValidateRecoveryCode`. A single mistyped character produces a well-formed code that derives a **different, valid-looking** challenge key. Today the only way to notice is:

1. **Online:** sign the server's challenge with the derived key and let Houston compare it with the stored challenge public key. This needs a centralized service.
2. **Offline (Recovery Tool):** decrypt the encrypted user key from the Emergency Kit. `decryptWithPrivKey` uses AES-CBC with no MAC (`encrypt.go:367`), so a wrong code "decrypts" silently into garbage. The error only shows up later, when the derived keys find no funds or don't match the kit's fingerprints.

### 1.3 Goal

Add a checksum to the code so that **any wallet or tool can tell, offline and instantly, whether a typed code is well-formed and free of typos**. The checksum must:
- have hard guarantees for the errors people actually make
- be able to point the user at a single typo
- cost no entropy

### 1.4 Non-goals and a key clarification

- A checksum proves that **a code is internally consistent.** It does *not* prove that the code belongs to *this user*. Ownership can still be proven by the server challenge, or offline by decrypting the kit key and comparing BIP32 fingerprints with the kit's `FirstFingerprint`/`SecondFingerprint` (see Phase 3). What the checksum removes is the need to contact a server just to find out whether the user made a typo.
- Existing v2 users are not migrated. v2 stays parseable and derivable forever, because funds depend on it.
- The key derivation function is not changed (see §2.5).

## 2. Format design (v3)

### 2.1 Layout: 9 blocks of 4

v3 keeps v2's 32 symbols unchanged (header + 30 random) and **appends a ninth block of 4 checksum symbols**. That makes 36 symbols, shown as 9 blocks of 4: 44 characters with dashes.

```
 L B r r - r r r r - r r r r - r r r r - r r r r - r r r r - r r r r - r r r r - C C C C
 ^ ^ ^------------------------- 30 random symbols --------------------------^   ^-----^
 | version = Alphabet[3-2] = 'B'                                                checksum block
 prefix                                                                         (2 × 2 symbols)
```

Example (generated by the reference script): `LBDR-DNMK-LMVA-N9BL-JQ5P-P4XU-F7TP-S5BL-FVJN`

The version char decides the expected length: `LA…` means 8 blocks (39 chars) and `LB…` means 9 blocks (44 chars). Clients can therefore adjust their input UI as soon as the first block is typed.

### 2.2 Decision record: why 9×4

We compared three layouts. All of them can be verified offline.

| | 8×4, 2 checksum | **9×4, 4 checksum (chosen)** | 8×5, 5 checksum |
|---|---|---|---|
| Characters to write down | 32 | **36** | 40 |
| Entropy | 137.4 bits (gives up 2 random chars) | **147.2 bits (same as v2)** | 161.9 bits |
| Errors always detected | 1 wrong char, or a swap | **any 2 wrong chars (including swaps)** | any 3 wrong chars in the first 7 blocks |
| Random garbage accepted | ≈ 1 in 900 | **≈ 1 in 810,000** | ≈ 1 in 22.7 million |
| Locates a single typo | no | **yes** | yes |
| Checksum is its own block | no | **yes (block 9)** | yes (block 8) |
| Client UI change | minimal | add a 9th box | every box goes from 4 to 5 chars |

9×4 keeps v2's full entropy, catches every 2-character error and can point at a single typo, all for only 4 extra characters to write down. 8×5 adds 15 bits nobody needs and a marginal detection gain, at the price of 8 characters (25%) more than v2 on a hand-written backup.

### 2.3 Checksum algorithm: two weighted sums mod 887

Let `body` be the first 32 symbols of the dash-stripped code (`L`, the version char and the 30 random symbols), and let `idx(c)` be the index of `c` in `Alphabet` (0–29).

```
P  = 887                                         // largest prime < 30² = 900
S1 = ( Σ_{i=0..31} (i+1)   · idx(body[i]) ) mod P
S2 = ( Σ_{i=0..31} (i+1)²  · idx(body[i]) ) mod P

enc(v)   = Alphabet[v / 30] ++ Alphabet[v % 30]   // 2 symbols per sum
checksum = enc(S1) ++ enc(S2)                     // block 9
```

**Decoding:** `dec(c0 c1) = idx(c0)·30 + idx(c1)`. Reject the code if either decoded value is `≥ 887`, or if `(dec(block9[0:2]), dec(block9[2:4])) ≠ (S1, S2)`.

This is a 2-check Reed–Solomon-style code over GF(887): the weights `(i+1)` and `(i+1)²` form a Vandermonde system. P is prime and every weight (1–32) and every symbol difference (1–29) is smaller than P, which gives the guarantees below.

**Detection guarantees** (brute-force verified: 0 misses over every single error, every transposition and a sample of double errors, anywhere in the 36 symbols)

| Error type | Detection | Why |
|---|---|---|
| Any 1 wrong symbol, anywhere | **100%** | A body error gives syndrome `(w·e, w²·e) ≠ 0`. A checksum-symbol error shifts a decoded value by a nonzero amount < 900. A shift of exactly ±887 leaves the range `[0, 887)` and is rejected. |
| Any 2 wrong symbols, anywhere | **100%** | Two body errors: the Vandermonde determinant `w_a·w_b·(w_b−w_a) ≠ 0`. A body error plus a checksum error: one syndrome component remains `w^k·e ≠ 0`. Two checksum errors: covered by the range check plus the nonzero shift. |
| Any transposition, adjacent or not | **100%** | A transposition is a 2-symbol error |
| Arbitrary random corruption | ≈ 1 in 810,000 accepted | (1/900)² |
| v2 code with its version char flipped to `B`, or v3 flipped to `A` | **100%** | The length no longer matches the version |

### 2.4 Single-typo location

Because the code detects every 2-symbol error, it can also **pinpoint any single wrong symbol**. Compute the syndrome `d1 = S1 − dec(block9[0:2])` and `d2 = S2 − dec(block9[2:4])` (mod P):

- `d1 ≠ 0` and `d2 ≠ 0`: the typo is in the body at position `w = d2 / d1` (1-based). The correct symbol is `idx = idx(body[w−1]) − d1 / w`. Accept this only if `1 ≤ w ≤ 32` and the corrected index is in `0..29`.
- Exactly one of `d1`/`d2` is 0, or a block-9 value is out of range: the typo is in block 9. Recompute it from the body.
- Otherwise there are 2 or more errors. Report "typo detected", with no location.

Verified: 37,120 / 37,120 single body typos were located and corrected to the original code.

**UX rule:** a located typo is a **suggestion only** ("Block 5, character 3: did you mean `K`?"). Never auto-apply it. With 3 or more errors, the "correction" could land on a different valid code, which would derive the wrong key. The server challenge or the kit fingerprints still confirm ownership after the user accepts.

### 2.5 Key derivation

Keep `HMAC-SHA256("muun:rc", canonicalCode)`, where `canonicalCode` is the full 44-char dashed uppercase string, including block 9. This is the same function as v2.

- Domain separation from v2 is already implicit, because the version char and the length are part of the HMAC input.
- No change is needed in Houston, in the encrypted-key format (`challenge_public_key.go`) or in the Emergency Kit encoding. The salt stays zeroed, as for v2.
- Entropy comes only from the 30 random symbols (147.2 bits). The checksum is a deterministic function of the body: it adds no entropy and leaks nothing.
- The canonical form must be byte-exact. Phase 1 adds a `Normalize` helper so that every client feeds the same string into the derivation.

## 3. Scope

This plan covers **libwallet only**: the `recoverycode` package, the gomobile bridge and their docs.

- **Out of scope:** Houston (backend), Apollo/Falcon (apps) and the Recovery Tool. What those consumers would need to do to adopt v3 is written up as integration notes in the docs (Phase 2), not planned here.
- **v3 is opt-in and never the library default.** `CurrentVersion`, `Generate()` and `GenerateRecoveryCode()` stay on v2. v3 codes are produced only through an explicit `GenerateVersion(3)` / `GenerateRecoveryCodeWithVersion(3)` call. Shipping this release changes nothing for existing consumers: they gain v3 parsing and validation, and they generate v3 only if they choose to.
- v1, v2 and v3 are all supported for parsing and derivation, with no sunset date.

## 4. Phases

### Phase 0: Specification and test vectors (≈ 2–3 days)

**Deliverables**
1. Write `recoverycode/SPEC.md` with the layout, the alphabet, the version→length rule, the checksum formula, the typo-location algorithm, the canonicalization rules, the KDF and the error taxonomy. Make it detailed enough for an outside wallet to implement without reading Go.
2. Create `recoverycode/testdata/v3_vectors.json`: about 60 vectors of `{code, valid, error_kind, privkey_hex, suggested_fix?}`. Cover:
   - valid v3 codes, including ones where S1 or S2 lands near the edges (0, 886)
   - **detection:** bad checksum, a block-9 value ≥ 887, a single substitution in each block, an adjacent and a distant transposition, two substitutions
   - **length and version:** a v3 body with only 8 blocks, a v2 code with 9 blocks, unknown version `C`, bad dash positions
   - **normalization:** lowercase input, spaces, missing dashes
   - **location:** a single typo in the body (expect the fix), a single typo in block 9 (expect the recomputed block), a double typo (expect no suggestion)
   - unchanged v1 and v2 vectors, to prove there is no regression
3. Get internal crypto/security review sign-off on the checksum construction and on keeping the KDF unchanged. Entropy is unchanged from v2.

**Exit criteria:** the spec has been reviewed and the vectors are frozen. All later phases test against the same file.

### Phase 1: libwallet implementation (≈ 1–1.5 weeks)

**1a. `recoverycode/recoverycode.go`**

- Split the single version constant, and add the layout constants:
  ```go
  // CurrentVersion is the version Generate() produces. It stays 2;
  // v3 is opt-in through GenerateVersion(3).
  const CurrentVersion = 2
  // LatestVersion is the highest version this library can parse/derive.
  const LatestVersion = 3

  const (
      blockSize        = 4
      v2Symbols        = 32         // 8 blocks
      v3Symbols        = 36         // 9 blocks
      checksumModulus  = 887
      checksumSymbols  = 4
  )
  ```
- Add the checksum primitives (unexported):
  ```go
  func computeChecksum(body string) (s1, s2 int)    // over the 32 body symbols
  func encodeChecksum(s1, s2 int) string            // 4 symbols (block 9)
  func decodeChecksum(block string) (s1, s2 int, ok bool) // ok=false if a value >= 887
  ```
- Add typo location:
  ```go
  // LocateTypo returns the 0-based symbol position (dashes excluded) of a
  // single-symbol error and the corrected code, or ok=false if the code is
  // valid or has 2+ errors.
  func LocateTypo(code string) (position int, corrected string, ok bool)
  ```
- Add sentinel errors so that callers can show specific messages. Wrap them with the existing `errors.New(code, msg)` pattern so that gomobile callers get codes through `ErrorCode()`:
  ```go
  var (
      ErrInvalidLength     = ...
      ErrInvalidCharacters = ...
      ErrUnknownVersion    = ...
      ErrInvalidChecksum   = ...   // the new one: "looks like a typo"
  )
  ```
- Rewrite `Version(code)` to choose the length by version instead of hardcoding 39:
  1. If `code[0] != 'L'`, it is the legacy path: require 39 chars and `AlphabetLegacy` → v1. This is unchanged.
  2. Otherwise, read the version from `code[1]`. If it is above `LatestVersion`, return `ErrUnknownVersion`.
  3. The expected length is 39 for v2 and 44 for v3. On a mismatch, return `ErrInvalidLength`.
  4. Check the alphabet and the dash positions. Generalize `validateAlphabet` to take the expected block count.
  5. If `version >= 3`, verify block 9. On a mismatch, return `ErrInvalidChecksum`.
- Update `ConvertToKey`: make it `case 2, 3:` (same HMAC). Add a `default:` that returns an error. Today an unexpected version falls through with `input == nil`, which would derive a key from an empty seed. Fixing that is a latent-bug hardening.
- Add `Normalize(code string) (string, error)`: trim, uppercase and drop all whitespace and dashes. Read the version from symbol 2 and require exactly 32 (v2) or 36 (v3) symbols, then re-insert a dash every 4 symbols. v1 codes pass through with 32 symbols. Callers use it before `Validate` and `ConvertToKey`. Keep `Validate` strict, with no implicit normalization, so that the derivation input stays explicit.
- Refactor `Generate()` into an internal `generate(version int) (string, error)`. It builds the body (header + 30 random), appends the checksum when `version >= 3`, and calls a shared `format(symbols)` that inserts the dashes. This replaces the current interleaved dash logic. Add `GenerateVersion(version int) (string, error)`, which accepts 2 or 3. `Generate()` returns `generate(CurrentVersion)`.

**1b. Root gomobile bridge, `recoverycode.go`**

- `GenerateRecoveryCodeWithVersion(version int) (string, error)`
- `NormalizeRecoveryCode(code string) (string, error)`
- `LocateRecoveryCodeTypo(code string) *RecoveryCodeTypo`. It returns a gomobile-friendly struct `{Block int, Index int, Suggested string}`, or `nil`. `Block` and `Index` are 1-based, which suits UI copy.
- `RecoveryCodeLatestVersion = recoverycode.LatestVersion` (a const)
- `RecoveryCodeBlockCount(versionChar string) int`, which returns 8 or 9, so that an input UI can size itself after block 1.
- In `errors.go`, add the codes `ErrInvalidRecoveryCode = 7` and `ErrInvalidRecoveryCodeChecksum = 8`, so that callers can tell "typo" apart from "not a recovery code".
- Leave `GenerateRecoveryCode()`, `ValidateRecoveryCode()`, `RecoveryCodeToKey()` and `GetRecoveryCodeVersion()` with unchanged signatures and unchanged v2 behavior.

**1c. Tests**

- Run the table-driven test against `testdata/v3_vectors.json` in both `recoverycode` and the root package.
- Exhaustive property tests: for a few random v3 codes, **every** single substitution (36 × 29), **every** transposition and **every** double substitution (C(36,2) × 29² ≈ 530k per code, which is fast in Go) must fail `Validate`. This is the Go port of the reference script.
- Location property: for random v3 codes, every single body substitution must give a `LocateTypo` result that equals the original code. Every block-9 substitution must give the recomputed block. For double substitutions, the test only records how often a suggestion appears. One can, because a code 2 errors from the original may be 1 error from a *different* valid code. That is why suggestions are hints only (§2.4).
- Round-trip: `GenerateVersion(3)` → `Validate` → `Version == 3` → `ConvertToKey` succeeds, repeated 10k times.
- Default unchanged: `Generate()` and `GenerateRecoveryCode()` still return v2 codes.
- Distribution sanity: over 100k generated codes, S1 and S2 each cover all of [0, 887).
- `FuzzVersion`, `FuzzNormalize` and `FuzzLocateTypo` (Go 1.18+ native fuzzing; `go.mod` is at 1.14, so bump it or use `go-fuzz`). Assert no panics and that `Normalize(Normalize(x)) == Normalize(x)`.
- **Fix the existing test.** `TestValidate/"invalid version"` uses `LB2Q-…` (39 chars). That now parses as v3 and fails on *length* rather than the version. Change it to `LC…` for "unknown version" and add separate cases for "v3 with 8 blocks" and "bad checksum".
- Regression: the v1 and v2 `TestConvertToKey` expected keys must stay byte-identical.

**Exit criteria:** v3 parse, validate, locate and opt-in generate are implemented, v2 remains the default, and CI is green.

### Phase 2: Documentation and release (≈ 2–3 days)

- Finalize `recoverycode/SPEC.md` against the implementation, and add godoc for every new exported symbol.
- Add a **"Recovery code versions"** section to `README.md`: the formats, the opt-in v3 API and a link to the spec and vectors.
- Add an **"Integration notes for consumers"** section to `SPEC.md`. This is the only place downstream work is mentioned. It covers:
  - **The safety rule:** don't generate v3 codes for users until every tool they might need for recovery (apps, recovery tooling) runs a libwallet version that can parse v3. Older libwallet rejects 44-character codes.
  - Call `NormalizeRecoveryCode` before validating or deriving, so that every consumer derives from the same string.
  - Input UIs must accept both 8 and 9 blocks, and `RecoveryCodeBlockCount` tells them which. Setup flows should make sure users write down all 9 blocks.
  - Map the new error codes to distinct messages: "typo detected" versus "not a recovery code".
  - Show `LocateRecoveryCodeTypo` output only as a suggestion the user must accept, never apply it automatically.
  - Optionally, gate v3 generation behind a server-side flag, so that adoption can be controlled per user.
- Write release notes and tag the libwallet release.

**Exit criteria:** the docs are merged and the release is tagged.

### Phase 3 (optional follow-ups, libwallet only)

These are independent and lower priority. Each could be its own PR.

1. **Offline ownership check.** Add `VerifyRecoveryCodeAgainstKit(code, encryptedUserKey, expectedFingerprint)`, which derives the key, decrypts and compares the BIP32 fingerprint with the kit's. Combined with the checksum, this gives full offline verification ("valid *and* yours") without a server.
2. **Version-char and missing-block hints.** A 36-symbol code starting `LA…` fails on length. If its body passes the v3 checksum with `B` in position 2, suggest "did you mean `LB…`?". Likewise, for an 8-block code starting `LB…`, report that block 9 is probably missing instead of a generic length error.

## 5. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| A consumer generates v3 codes before its recovery tooling can parse them | Users locked out of funds | v3 is opt-in only, never the default; the safety rule leads the integration notes |
| Callers disagree on the canonical string (spaces, case, dashes) | Wrong key derived | `Normalize` is the single source of truth, plus shared vectors |
| A typo suggestion is applied to a code with 3+ errors | Wrong key derived | The API is documented as hint-only (§2.4, integration notes) |
| Off-by-one in weights, packing or the location formula | Valid codes rejected or bad suggestions | Frozen vectors, exhaustive property tests, edge vectors near 0 and 886 |
| Existing test `LB…` now means v3 | Spurious CI failure | Update it in Phase 1 (noted in 1c) |
| `ConvertToKey` silent nil-input path | Derives a key from an empty seed | Add a `default:` error case in Phase 1 |
